# DNS servers for a home router in Russia (as of 20 Aug 2026)

Compiled from open sources. Compilation date: 20 August 2026.

## Overall picture of DNS blocking in Russia

- In 2021, the first blocks of Google DNS (8.8.8.8, 8.8.4.4), Cloudflare (1.1.1.1, 1.0.0.1), and Cisco OpenDNS (doh.opendns.com) were
  recorded across all three protocols — plain UDP DNS, DoH, and DoT. For DoH/DoT, a TCP RST was applied after the TLS ClientHello (SNI-based
  blocking); for UDP, packet loss. The blocking was intermittent: the same server could work and then fail on the same ISP.
  [Source: github.com/net4people/bbs #81](https://github.com/net4people/bbs/issues/81)
- In summer 2025 (~10 June), Roskomnadzor (RKN) added a substantial share of Cloudflare subnets to the registry of banned resources;
  Cloudflare traffic in Russia dropped by about 30%. The stated reason was the expansion of TLS ECH, which RKN treats as a violation of the
  law. [Source: habr.com/ru/news/922532](https://habr.com/ru/news/922532); [fontanka.ru](https://www.fontanka.ru/2025/04/02/75295799/)
- In 2026, RKN tested blocking of public DNS 1.1.1.1 and 8.8.8.8 (and related URLs) in a targeted way, from 21:00 to 22:00, on several large
  ISPs.
  [Source: ru.wikinews.org](https://ru.wikinews.org/wiki/%D0%A0%D0%BE%D1%81%D0%BA%D0%BE%D0%BC%D0%BD%D0%B0%D0%B4%D0%B7%D0%BE%D1%80_%D1%82%D0%B5%D1%81%D1%82%D0%B8%D1%80%D1%83%D0%B5%D1%82_%D0%BC%D0%B0%D1%81%D1%81%D0%BE%D0%B2%D1%83%D1%8E_%D0%B1%D0%BB%D0%BE%D0%BA%D0%B8%D1%80%D0%BE%D0%B2%D0%BA%D1%83_%D0%BF%D1%83%D0%B1%D0%BB%D0%B8%D1%87%D0%BD%D1%8B%D1%85_DNS-%D1%81%D0%B5%D1%80%D0%B2%D0%B8%D1%81%D0%BE%D0%B2_Google_%D0%B8_Cloudflare)
- In February 2026, the domains of YouTube, Facebook, WhatsApp, and several foreign media outlets were removed from Russia's NSDI (National
  Domain Name System).
  [Source: asiaplustj.info](https://www.asiaplustj.info/en/news/world/20260212/russia-removes-whatsapp-facebook-youtube-and-major-news-sites-from-national-dns-servers)
- A te-st.org study dated 7 August 2026 identified 3 classes of DNS resolver anomalies in Russia:
    - **Class A** (Google, AdGuard): answers are substituted only for blocked domains (Signal, Telegram, BBC, Meduza) — returning IPs
      8.47.69.6 / 8.6.112.6. The effect depends on the route inside Russia and appears even when using DoH/DoT.
    - **Class B** (Yandex DNS, NSDI): return sinkhole IPs 8.47.69.0 / 8.6.112.0 from all nodes, affecting even the control domain
      cdnjs.cloudflare.com.
    - **Class C** (Cloudflare, NextDNS): substitution occurs only from the service's Russian nodes.
      [Source: te-st.org, 07.08.2026](https://te-st.org/2026/08/07/dnsdnsdns/)
- By April 2026, RKN had blocked more than 469 VPN services; WireGuard, OpenVPN, and L2TP protocols were fully blocked “in the clear”;
  YouTube was throttled to ~128 kbps. Domain fronting via Cloudflare was shut down.
  [Source: habr.com/ru/articles/1007570](https://habr.com/ru/articles/1007570)
- Cloudflare (including WARP) in Russia works **unreliably**, rather than being fully blocked: some subnets are cut by DPI/SNI (primarily
  due to TLS ECH); availability varies by domain, operator, and region, and can change without warning.
  [Source: dimaserbun.ru](https://dimaserbun.ru/en/blog/cloudflare-v-rf-pochemu-otkazalsya/);
  [enterno.io](https://enterno.io/en/articles/cloudflare-in-russia)

**Key takeaway:** simply switching DNS servers (even encrypted DoH/DoT) does not guarantee access to blocked sites — SNI/DPI blocking at the
TCP/TLS connection level runs in parallel and does not depend on which DNS you use to resolve the domain. DNS only solves the problem of
**answer correctness** (so the ISP does not inject a fake IP), not the problem of **access** if the site is cut at the DPI layer.

## 4. Router setup

- **Keenetic**: natively supports DNS-over-TLS via the **DNS-over-TLS proxy** system component (port 853) — among mass-market home routers,
  this is the best built-in encrypted DNS support. Install it under **Management → System settings → Component options**. Then configure
  servers at **Internet safety → Network rules → DNS configuration** (Add server; TLS domain name; port 853 is filled in automatically).
  [support.keenetic.com](https://support.keenetic.com/explorer/kn-1613/en/25049-dot-and-doh-proxy-servers-for-dns-requests-encryption.html),
  [vpnkeenetic.ru](https://vpnkeenetic.ru/obkhod-blokirovok-keenetic/),
  [trofimovsky.ru](https://trofimovsky.ru/article/dns-na-routere-2026-kak-pomenyat-i-nastroit-keenetic-tp-link-asus-rostelecom/)
- **ASUS**: has a built-in DoT feature. Path: **WAN → Internet Connection**. Set **DNS Privacy Protocol** from None to **DNS-over-TLS
  (DoT)** and add servers (IP Address / TLS Hostname). Plain WAN DNS is under **WAN DNS Setting** (switch off automatic WAN DNS if you want
  manual servers). [asus.com/support/faq/1051428](https://www.asus.com/support/faq/1051428/)
- **TP-Link**: only plain unencrypted DNS via `tplinkwifi.net` → **Advanced → Network → Internet** → Advanced Settings → **Use the following
  DNS addresses** (Primary DNS / Secondary DNS) — DoH/DoT is absent on most models.
  [tp-link.com/support/faq/1712](https://www.tp-link.com/us/support/faq/1712/)
- **MikroTik**: supports DoH via the `use-doh-server` parameter in DNS settings.

⚠️ Plain (unencrypted, port 53) DNS on the router is physically visible to the ISP and can be substituted/cut by SNI regardless of which DNS
is specified — so where protection against substitution matters, you need DoH/DoT/DoQ, not merely a change of DNS server IP.

## 5. Separate issue: foreign DNS breaks routing specifically for Russian sites (not blocking, but ECS/CDN geolocation)

This is not a DPI effect and not censorship — it is how CDNs work via EDNS Client Subnet (ECS):

- CDNs (including Russian ones — Yandex, Sber, VK, and others) return the IP of the “nearest” edge server depending on where the DNS query
  came from. This usually uses **ECS** — a DNS extension in which the resolver sends the authoritative server a portion of the client's IP
  subnet so it can pick a geo-optimal answer.
  [developers.google.com/speed/public-dns/docs/ecs](https://developers.google.com/speed/public-dns/docs/ecs)
- Google Public DNS states that it supports ECS and passes a **partial** client IP to authoritative servers — but this only works if the
  specific CDN/site actually supports and trusts ECS from Google. Large CDNs (e.g. Akamai, Fastly) deliberately restrict which resolvers
  they answer honestly on ECS, for abuse-protection reasons.
  [developers.google.com/speed/public-dns/docs/ecs](https://developers.google.com/speed/public-dns/docs/ecs),
  [farrokhi.net](https://farrokhi.net/posts/2025/10/edns-client-subnet-in-practice-evaluating-public-resolver-behaviors/)
- If the site/CDN does not support ECS (or does not trust the specific resolver), client geolocation is determined by **the DNS resolver's
  own IP** — that is, by the nearest Google/Cloudflare/Quad9 anycast point, not by the user's actual location in Russia. As a result, a
  “Russian” CDN may return an edge-server IP that is physically abroad — hence slow or unstable performance even for fully Russian,
  unblocked sites when using foreign DNS. Independent measurements confirm that with such a mismatch between resolver and CDN, the
  performance drop can reach 20–40% (Akamai example).
  [cdnplanet.com — Real-world CDN performance for Google DNS and OpenDNS users](https://www.cdnplanet.com/blog/real-world-cdn-performance-googledns-opendns-users),
  [arxiv.org/html/2502.05763v1 — Public DNS Resolvers Meet CDNs](https://arxiv.org/html/2502.05763v1)
- Against the backdrop of degraded international transit links for Russia in 2025–2026 (see section 1), this problem is felt more sharply:
  if the CDN answer steers traffic via a foreign route rather than a local peering point, latency and loss grow more than before.

**Practical takeaway:** for Russian sites and services it is better to resolve via Russian DNS (Yandex DNS, BI.ZONE Public DNS, Comss.one,
the ISP's own DNS), and to attach foreign/encrypted DNS (Cloudflare, Quad9, AdGuard, Mullvad) selectively — only for domains that Russian
DNS does not resolve correctly (blocked/foreign resources). That is the split-DNS / per-domain conditional routing mentioned in section 1 as
a circumvention method (dnsmasq on the router, or AdGuard Home with `upstream` rules by domain masks — on routers that support this, e.g.
via a custom firmware/OpenWrt, not “out of the box” on TP-Link/ASUS/Keenetic).

## 6. Practical conclusions from the collected facts

1. There is no fully “unblockable and fastest-for-everyone” DNS — the result depends on the specific ISP, region, and moment in time
   (securitylab.ru notes this directly, 30.04.2026: “there is no universally correct DNS for the whole country”; it recommends keeping at
   least two profiles to switch between). [securitylab.ru](https://www.securitylab.ru/blog/personal/Bitshield/360502.php)
2. Russian DNS (Yandex, BI.ZONE, Comss.one) give the lowest latency inside Russia and are not blocked, but they are required to enforce the
   RKN registry — they do not lift blocks on specific banned domains.
3. Foreign DNS (Cloudflare, Google, Quad9, Mullvad, Control D) are not subject to RKN, but some of them (Google, AdGuard) still substitute
   answers specifically for blocked domains — likely due to traffic interception at the ISP network layer, not the DNS service itself.
4. For real access to resources blocked by DPI/SNI (not just DNS substitution), a DNS change alone is not enough — you additionally need a
   VPN/proxy with obfuscation (WireGuard/OpenVPN are blocked “in the clear”; only masquerading protocols such as VLESS+Reality and XRay
   work).
5. Among built-in router solutions, Keenetic has the best support for encrypted DNS (DoT).
